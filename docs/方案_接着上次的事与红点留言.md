| 来源 | 处理 |

**第二轮审核（同日）**：四条全部采纳，都不需要加管理页面或已读确认。

| 意见 | 处理 |
|---|---|
| 1. 他已经说了结果，红点还会去问 | 整理时可以返回已有事项里"已经有结果或取消了"的 id，这些直接改成 `closed`，不再问。验收时，"说计划"和"报结果"分两次整理（§3.4、§3.5、§5） |
| 2. 普通进聊天可能领走另一张卡的留言 | 只有点了带红点的卡，页面才传 `follow`（id）。服务器在锁内核对：它仍是首页选中的那一件，并且属于这个自己。没传就是普通开场，永远不领 |
| 3. 早发出、晚回来的 `/api/self` 会把刚清掉的红点画回来 | 页面记下清红点的时间，比这个时间早发出的 `/api/self` 带回来的 `due` 一律不用。加一个页面用例：故意让一个带旧 due 的响应晚回来 |
| 4. 冒烟测试要看未来的事项，但接口只返回当天该问的 | `/api/self` 只返回 `due: {id, p}`，不返回事项列表。"一句话记下、日期对"放到离线测；"当天没有红点、到期才出现"放到页面测 |

**第三轮审核（实现之后，同日）**：四条全部采纳。

| 意见 | 处理 |
|---|---|
| 1. 他报了结果、整理还没完成时，红点仍会亮、仍能领走 | 只要他还有没整理的话（`msgs > folded`），就不出红点、也领不到：结果可能就在那几句里。首页和领取共用 `_follow_pick`，判断一致。页面回首页时会先整理（`/api/sync`），整理完再刷新，所以平时不受影响 |
| 2. 两次刷新乱序时，已关掉的红点会画回来 | 页面给每次 `/api/self` 编号，红点只认最新回来的那一次；清红点时，已发出的请求一律作废。这样替换了原来按时间判断的 `DUE_CLR` |
| 3. 午夜前领了 A、次日领了 B，A 才失败，次日的名额被还回去 | `follow_take` 记下用的是哪天；`follow_undo` 总是把 A 放回 open，但只有 `follow_day` 还是那天时才恢复 |
| 4. 留言的 40 字上限被放宽了 | 留言开场按 40 字截（`FOLLOW_MAX`，和 `fit` 一样不算空白），普通开场仍是 80 字；真模型评测也按 ≤ 40 字检查 |

**第四轮审核（同日）**：两条都采纳。

| 意见 | 处理 |
|---|---|
| 1. 他报完结果、回复还没生成就回首页，仍能领到这件事的留言（他的话要等回复生成后才落盘） | 服务器从收到这一轮发言起就记下"正在回复"（`Memory.talk`，包在 `App.chat` 外面），期间不出红点、领不到；回复落盘后，再按"有没整理的话"继续暂停到整理完 |
| 2. 回首页时后台正在整理，`/api/sync` 直接返回，红点要等下次刷新才出 | 整理改成每个用户一把锁：`/api/sync` 最多等 20 秒，等正在跑的那次做完，再整理剩下的（多半没有剩下，不再调模型）；聊天里触发的后台整理照旧不等。页面上 `/api/sync` 失败也照样刷新一次 |

## 1. 这一轮验证什么

两个场景，客户演示时并排展示：

- **场景一，我回来接着昨天的话说，它接得住。** 来自用户 B："忙完以后想去继续聊"。
- **场景二，我没开口，它也会为一件具体的事留一句话。** 来自用户 A："主动发消息关心"。

  只做打开网页时看到的红点，不做手机通知。所以本轮只能回答"他回到首页后，会不会点开留言、会不会接着聊"，回答不了"留言能不能把他拉回来"。

**不变的规则：** 11-24 客户说过"老是在说昨天的事"，所以"回来只打招呼、不主动提旧事"这条照旧（`server/mylife_server.py:1621-1633`）。场景一是他自己提，场景二是一件事只提一次，两个场景都不违反这条规则。

## 2. 场景一：他自己回来接着聊

### 2.1 现状

| 情况 | 现在能不能接住 |
|---|---|
| 昨天聊了几句，已经整理进记忆 | **能**。上下文里有"最近几次聊天"（`memory.py:664-667`）和记住的事 |
| 昨天的话还没整理（只说了一两句；或者关掉页面、还没触发整理），今天找**同一个**自己 | **不能**。页面只发这一次的聊天（`sessionMsgs`，2 小时没说话就算新一次），服务器又只补另一个自己没整理的话（`memory.py:647-648` 的 `r.get("p") != pid`）。已在临时目录复现：同一个自己看不到，另一个自己看得到 |
| 昨天聊的、今天整理的 | 能接住，但这次聊天在记忆里记成了今天的日期（`memory.py:589` 用整理当天的 `_today()`），他说"昨天那个"时容易对不上 |

### 2.2 改动（两处，各一两行）

1. **`memory.py:647-648` `context`：** 没整理的话里，同一个自己说的也补上，但只补 2 小时以前的；2 小时内的已经在页面发来的这一次聊天里。
2. **`memory.py:589` `consolidate`：** 这次聊天的日期改成取最后一句的日期（`new[-1]["t"][:10]`），不再用整理当天的日期。

### 2.3 验收（用同一段对话测两个结果）

前一天跟伙伴聊过"和同事小王因为周报闹别扭"，聊到一半离开。分两种情况测：已整理，和只说了一句、还没整理。

- 今天说"接着昨天那个说吧"：两个自己都能接回小王、周报这件事。
- 今天说"帮我算一下午饭热量：一碗牛肉面"：直接算热量，不提小王。

## 3. 场景二：红点留言

### 3.1 用户看到的效果

1. 周四他跟导师说："明天下午面试，有点慌。"
2. 周六他打开网页，导师卡片右上角出现红点，"上次：……"那一行换成"有一句话留给你"。不写具体是什么事，避免手机被别人看到时泄露隐私。
3. 点进去，第一句话是关于那件事的：
   - 导师可以问一句："周五那个面试去了吗，感觉怎么样。"
   - 伙伴不用问号："周五的面试应该过去了。想说说就说，不想说也没事。"
4. 他接着聊、换话题都行。这件事不会再提，红点消失。

### 3.2 日期规则（全文以这个例子为准）

| 周四 | 周五 | 周六 | 周日 | 周一 | 周二 |
|---|---|---|---|---|---|
| 说"明天面试" | 面试当天，**不问** | 可以问（due） | 可以问 | 可以问 | 作废 |

- `due` = 事情发生的第二天。
- 可见的条件：`due <= 今天 <= due + 2`，正好 3 个自然日。
- 两个自己合计每天最多问一件。同时有几件可以问时，取 due 最早的。
- 他还有没整理的话时，暂不出红点、也领不到（第三轮审核 1）。

### 3.3 数据

存在 `users/<uid>/self.json` 里新加的字段。清空时整个目录一起删，清空逻辑不用改。

```json
"follows": [{"id": "a1b2c3d4", "text": "你周五下午有个面试", "due": "2026-11-28", "p": "bange", "state": "open"}],
"follow_day": "2026-11-28"
```

- `state` 有三种：
  - `open`：等着问；
  - `asked`：问过了；
  - `closed`：他自己已经说了结果，或者说不去了。

  只有 `open` 才会被问。
- `p` 取这次整理里最后一句话是跟谁说的，也就是 consolidate 里已有的 `pid`（`memory.py:574`）。切换两个自己时就会触发整理，所以一次整理基本只有一个自己的话。
- 旧档案靠 `_empty_profile()` 的默认值兼容，不需要迁移。

### 3.5 提示词

**整理（加在 `CONSOLIDATE_PROMPT` 里）**

```
"follow": [{"text": "以“你”开头，什么事、哪天，不超过 30 个字", "due": "YYYY-MM-DD，事情发生的第二天"}],
"close": ["【等着问的事】里，这次他已经说了结果、或说了不去了/取消了的条目 id"]
规则：只记他亲口说的、一个月内会发生、之后会有结果的具体事（面试、考试、复查拿结果、跟谁谈某事、截止日、搬家之类），
按每段前面标的日期算“明天”“周五”是哪天；说不出哪天的不记；心情、长期的烦恼、AI 建议他做的、已经有结果的、
想死或伤害自己的话，都不记。最多 2 条，已有的不重复写，没有就给空数组。
close：只写他这次亲口说了结果（面完了、拿到结果了、谈过了）或说不去了、改期没定的；没有就给空数组。
```

**开场**

```
OPENING_FOLLOW = "【现在】他又来了，还没开口。他前几天说过：%s。这件事现在应该有结果了。你先开口，一两句，
不超过四十个字，就这件事说一句，%s。不说“上回”“我一直记着”“我记得你说过”，不猜结果好坏，不说恭喜也不说没关系；
他不想聊这个也行。"
导师：可以问一句怎么样了，只问一个问题；伙伴：不提问、不用问号，提一句，让他知道想说就说
```

## 4. 以后再说（第一版不做）

- 「我记得的事」里显示和删除待问的事。理由：只问一次、3 天就作废，影响有限；有人反感再加。
- 同一件事保证同一份留言，并由前端确认看到后才算问过。理由：第一版已经靠"先占住、失败放回"避免了问两次；剩下"服务器生成了、页面超时没显示"的情况很少，最坏也只是少一次关心。
- 一小时内说过话不出红点；按原话判断跟哪个自己说的；按相似度去重。
- 手机通知，也就是真正的主动消息。
- 角色设定（亲人、偶像、联系不上的人）。这是用户 A 的另一个诉求，要客户定方向。

## 5. 测试

1. **离线（`tools/follow_eval.py`，桩模型，临时目录，固定日期）：**
   - 按 §3.2 的例子，逐日检查周五到周二能不能看到；
   - 每天最多一件；
   - `follow_take` 只能拿到一次，`follow_undo` 能放回；
   - 领取的核对：另一个自己的 pid、不是今天选中的那件、旧 id、没传 fid，都领不到，也不占当天名额；导师和伙伴各有一件到期时，只有首页亮点的那件能领；
   - 说计划和报结果分两次整理：第一次记下（open），第二次给出 close，变成 `closed`，到期也不出红点；
   - 校验规则都生效：日期越界、命中 CRISIS、重复、超过上限，以及 close 里不是 open 的 id；
   - 只说一句也会整理：一句"后天下午去拿体检结果"离开对话，self.json 里就有这一条，due 正确；当天 `summary` 的 `due` 为 null；
   - §2.2 的两处改动；
   - 总开关。
2. **真模型（`tools/follow_eval.py --live`，合成对话，在本机用真的 `App`）：**
   - 场景一：§2.3 的两种情况，两个自己各 3 次；
   - 抽取：5 句该记的（明天面试、周五拿体检结果、下周一跟老板谈加薪、月底交初稿、后天搬家），5 句不该记的（好累、一直担心妈妈身体、AI 建议的、已经面完了、想死）。合格线：该记的至少 4 句记下且日期对；不该记的 0 句；
   - 报结果：先整理"明天面试"，再整理"面完了，拿到 offer 了"和"面试改期了，还没定"，两种都要给出 close；
   - 开场：两个自己各 5 次。要提到那件事、不超过 40 字、伙伴不用问号、不说"上回""一直记着"。
3. **页面（Playwright，Chrome 和 WebKit，用 route 模拟 `/api/self` 和 `/api/open`）：**
   - 红点出在对的卡上，点进去时 `/api/open` 带着这个 id，开场后红点消失；
   - 点没有红点的那张卡：`/api/open` 不带 follow，红点留在原来那张卡上；
   - `d.follow` 对不上时，红点不清；
   - 旧响应晚到：故意让一个带旧 due 的 `/api/self` 晚回来，等留言显示后再放行，红点保持消失；
   - 已经进过这个对话也能触发；
   - 清空后没有红点；
